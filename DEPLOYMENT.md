# AWS deployment

Delia deploys as a React SPA on AWS Amplify Hosting, a NestJS API on ECS Fargate behind an Application Load Balancer, and PostgreSQL 16 on RDS. Infrastructure is defined in `infra/` with Terraform.

## Release order

The deployment workflow deliberately applies Terraform in stages:

1. Terraform creates ECR, then CI pushes the immutable image.
2. Terraform creates the runtime dependencies and task definitions.
3. CI runs the migration task and requires exit code `0`.
4. Terraform creates or updates the ECS service and remaining resources only after migrations succeed.
5. CI uploads the already-built SPA to Amplify and smoke-checks `/api/ready`.

This ordering prevents a new API revision from receiving traffic before its schema is ready. The API image never runs migrations during ordinary task startup.

## Prerequisites

- An encrypted, versioned S3 bucket for Terraform state.
- A GitHub environment named `staging` (and later `production`).
- A GitHub OIDC IAM role trusted only by the repository and environment.
- An existing public Route 53 hosted zone if Terraform should configure custom domains.
- A Secrets Manager JSON secret containing every key listed below.

### Application secret JSON

When `APPLICATION_SECRET_ARN` is configured, the secret must contain all of these keys because ECS resolves them at task startup:

```json
{
  "GEMINI_API_KEY": "...",
  "GOOGLE_APPLICATION_CREDENTIALS_JSON": "{...service account JSON...}",
  "GOOGLE_CLOUD_PROJECT": "project-id",
  "GOOGLE_OAUTH_CLIENT_ID": "...",
  "GOOGLE_OAUTH_CLIENT_SECRET": "...",
  "SMTP_HOST": "smtp.example.com",
  "SMTP_USER": "...",
  "SMTP_PASSWORD": "...",
  "NOTIFICATION_FROM": "notifications@example.com"
}
```

The Google credential is written to an ephemeral file inside the task. It is never copied into the image. The application secret is required by the production task definition; integrations that are not enabled should still be represented by empty string values so ECS can resolve every configured key during task startup.

RDS credentials and the admin token are generated by Terraform in separate Secrets Manager secrets.

## GitHub environment configuration

Required variables:

- `AWS_DEPLOY_ROLE_ARN`
- `AWS_REGION` (for example `eu-central-1`)
- `TF_STATE_BUCKET` (a pre-created private S3 state bucket)
- `WEB_ORIGIN` (for example `https://app.example.com`)
- `API_ORIGIN` (for example `https://api.example.com`)
- `DESIRED_COUNT` (normally `1` for staging and at least `2` for production)

Required environment secret:

- `APPLICATION_SECRET_ARN`

Optional DNS/TLS variables:

- `HOSTED_ZONE_ID`
- `ROOT_DOMAIN`
- `API_DOMAIN_NAME` (defaults to `api.<ROOT_DOMAIN>`)
- `WEB_SUBDOMAIN` (defaults to `app`)
- `CERTIFICATE_ARN` (required for HTTPS on the load balancer)

## GitHub OIDC trust

The AWS role must trust GitHub's `token.actions.githubusercontent.com` provider and restrict `sub` to the intended repository environment, for example:

```json
{
  "StringEquals": {
    "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
    "token.actions.githubusercontent.com:sub": "repo:OWNER/REPOSITORY:environment:staging"
  }
}
```

Use a separate, more restricted role for production. Do not create long-lived AWS access keys for GitHub.

## First staging release

1. Configure the GitHub `staging` environment.
2. Run **Deploy AWS** from the Actions tab with `environment=staging`.
3. Confirm the migration task exits successfully.
4. Verify the workflow's API smoke check.
5. Verify login, chatbot, live voice, OAuth, email, booking confirmation, widget origins, and RAG ingestion manually.

## Local validation

```bash
npm ci
npm run lint
npm run typecheck
npm test
npm run build:platform
npm run test:smoke
terraform -chdir=infra init -backend=false
terraform -chdir=infra validate
```

`terraform validate` is read-only. `terraform apply` creates billable resources and should run only through an approved GitHub environment.

## Rollback

- API images use immutable Git SHA tags. Rerun the deployment with a previously known-good image tag to roll back application code.
- Database migrations must be forward-compatible. Never automate destructive down migrations.
- Production RDS has deletion protection, retained snapshots, encryption, and Multi-AZ enabled by the stack.
- The ECS deployment circuit breaker rolls back tasks that fail health checks.
